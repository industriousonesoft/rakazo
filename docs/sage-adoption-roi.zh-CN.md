# Sage 理念原生移植：ROI 评估

状态：设计评估，尚未实施或运行对照实验。评估日期：2026-10-03。

阅读顺序：本报告 → [移植方案](./sage-adoption-design.zh-CN.md) → [实施 Checklist](./sage-adoption-checklist.zh-CN.md)。

## 1. 投资结论

**值得投入有退出条件的双场景试点，暂不建议整体引入 Sage。** 对象是 Rakazo 内部 AI 员工；首期同时覆盖代码修改与 CSV 报表生成。

最大的增量价值是把“模型认为完成”变成“系统检查过指定条件”。这可以减少漏检、使用过期证据和未经验证的交付，但不能证明需求完整、测试充分或所有自然语言结论正确。

建议分阶段投入：先建立可复现基线，再实现两个验证器和最小共享机制。若现有能力已经满足目标、误阻断过多，或人工节省不足以抵消成本，应停止扩展。独立审查列为阶段 5 的可选实施项：阶段 4 完成后另行决定投入，不作为首期验收或发布前提，也不默认增加每次任务的调用成本。

本报告使用四类标记：**事实**为源码或文档可核查的现状；**上游证据**为 Sage 的特定实验；**建议**为拟实施设计；**估算**为尚需验证的投入及收益假设。

## 2. 当前基础与真正缺口

事实核查基线：Rakazo `70d08e76f1c367d205bccfd8454ead7ae7ae6425`。以下链接指向仓库文件；实现前应复查后续变更。

| 已有设施 | 可复用内容 | 不应计为新增收益的部分及剩余缺口 |
| --- | --- | --- |
| [执行器](../packages/adapters/src/executor.ts) | Run 租约、工具调度、审批、完成与恢复路径 | 运行结束不等于业务验收通过 |
| [外部操作记录](../packages/adapters/src/approval-effect.ts) | 请求绑定、受控操作去重、不确定结果处理 | 不能据此保证所有 shell、GUI 操作只执行一次 |
| [教学流程](../packages/core/src/teach-playbook.ts) | 步骤、检查方式、交付要求 | 文字要求尚不是统一强制验收 |
| [Pi 适配](../packages/adapters/src/pi-runtime.ts) | Agent 循环、子代理、后台 shell 收尾 | 需要将强制证据写入、交付检查与反馈闭环接入 |
| [数据库事件](../packages/db/src/events.ts) | 持久化事件与最终状态事务 | 审计事件不能自动等同验证证据 |
| [评估框架](./agent-verification.md) | 离线回归、真实模型评估、确定性裁判 | 评估通过不是每次生产任务都经过门禁 |
| 现有记忆与 Skills | 保存经验、按需提供操作规范 | 记忆不替代当前产物的检查，不引入第二套记忆系统 |

仓库评估文档记录过原始 15 个场景、每场景 3 次的修正后 45/45 基线，也说明当前场景已扩展。它是历史记录，不是本次复测，更不是所有岗位的可靠率。本次必须使用当前版本、当前模型重新建立基线。

## 3. 从 Sage 吸收什么

| 机制 | 增量价值判断 | 成本或风险 | 决策 |
| --- | --- | --- | --- |
| 交付前校验证据 | 高：减少未检查就报完成 | 检查规则可能不充分 | 首期 |
| 证据绑定产物与规则版本 | 高：防止旧检查覆盖新文件 | 摘要、并发与存储开销 | 首期 |
| 状态由执行事实生成 | 高：减少模型自报状态漂移 | 需要恢复与事务设计 | 首期 |
| 操作前门禁 | 中至高：阻止已识别的无效交付 | 任意 shell/GUI 难以全面拦截 | 首期限定结构化路径 |
| 按需工作规范 | 中：减少无关上下文 | Skill 选择仍可能遗漏 | 复用现有 Skills |
| 独立代理复核 | 未确定：适合部分复杂任务 | 延迟、Token 和共同错误 | 可选阶段 5，单独评估 |
| 全任务 TDD、规格审批 | 岗位依赖明显 | 简单任务承担过多流程 | 不作为默认 |
| 独立 cycle/manifest | 低：与 Run 状态重叠 | 双份状态可能不一致 | 不引入 |
| sage-memory / sage-wiki | 本次没有必要 | 数据治理及运维复杂度 | 不集成 |

上游证据：Sage 的 [eval-baseline](https://github.com/xoai/sage/blob/8ca22f4c671de9a2f35bbba616b7f078982a5977/docs/eval-baseline.md) 使用小样本测试，测试优先场景出现收益，但多个安全和任务场景与裸 Agent 持平；独立子代理流程增加明显成本。它支持“选择性验证机械约束”的方向，不支持把全部流程默认打开，也不能直接推导 Rakazo 的收益倍率。

Sage 的 [平台契约](https://github.com/xoai/sage/blob/8ca22f4c671de9a2f35bbba616b7f078982a5977/runtime/platforms/CONTRACT.md) 提供了有用的能力拆分：操作前阻断、操作后事件、子代理等。Rakazo 应声明实际能力并做符合性测试，不因接入几个 hook 就声称达到完整上游等级。

## 4. 投入估算

估算假设：一名熟悉 TypeScript、Rakazo 执行器及数据库的开发者；每人日约 8 小时；复用现有 UI 和测试框架。仅覆盖两个限定场景，不覆盖任意办公文件、自由文本事实核查或全面 GUI 防绕过。

| 阶段 | 人日 | 主要交付 |
| --- | --- | --- |
| 基线、场景、验收规则 | 3–5 | 合成数据、三组评估配置、指标 |
| 验证契约、持久化、执行器集成 | 6–10 | 状态与证据闭环、恢复处理 |
| 两个验证器 | 6–10 | 测试命令验证、CSV 核对 |
| 故障测试、跨端呈现、灰度 | 5–8 | 回归结果、开关与回退 |
| 合计 | **20–33** | 约 160–264 开发小时 |

这是规划区间，不是排期承诺。付费推理、评估等待时间与持续维护另计。若需要新增完整配置 UI、任意文件格式或外部交付回执，应重新估算。

## 5. 收益计算与敏感性

先统一成本单位，再计算：

```text
月净收益 = 月任务量 ×（每任务节省的人工验收及返工成本
                        − 每任务新增推理、计算及误阻断处理成本）
           − 月维护成本
回本月数 = 一次性投入 ÷ 月净收益
```

人工核验和返工分别计时，避免重复计算同一段时间。推理费用按实际计费；不可用的费用记录为空，不能填零。潜在严重事故单独分析，不编造发生概率，也不据此夸大回本。

示例假设：一次性投入折算 200 小时，月维护 8 小时，每任务净节省 6 分钟；额外计算费用已按同一人工费率换算扣除。

| 月任务量 | 月净节省 | 简单回本期 |
| --- | --- | --- |
| 50 | −3 小时 | 不回本 |
| 100 | 2 小时 | 100 个月 |
| 500 | 42 小时 | 约 4.8 个月 |
| 1,000 | 92 小时 | 约 2.2 个月 |

这些数字不是使用预测。低频个人使用可能主要获得透明度，不能假定有经济回报；重复性工作量大、验收条件明确的岗位更可能受益。

## 6. 如何测量真实增量

采用三组对照：A 为现有行为；B 为现有行为加同样的 Skill 验收规范；C 为 B 加原生质量门禁。每组的独立裁判和隐藏验收数据一致，不向 A/B 泄漏裁判答案。

固定模型版本、连接配置、输入、工具权限和总预算；交错执行三组；每次使用干净状态。每类 10 个场景、每场景每组 3 次，共 180 次。两类分别汇报，避免平均值掩盖某类退化。模型实际版本无法固定时必须注明。

| 指标 | 口径 |
| --- | --- |
| 合格交付率 | 独立裁判通过的任务数 / 所有计划试次；同时列出未完成与环境故障 |
| 错误完成声明率 | 被明确宣告完成但独立验收失败的任务数 / 有效试次 |
| 系统误认证 | 无有效证据却标记验证通过的次数；与自然语言夸大分开统计 |
| 误阻断率 | 独立裁判判断本可接受但被门禁错误阻止的次数 / 本可接受的候选交付数 |
| 人工成本 | 核验、纠错、误阻断处理分钟数 |
| 自动化成本 | Token、工具数、耗时、实际费用及每个合格交付的总成本 |
| 错误归因 | 模型、产品、供应商、评估环境、未完成分别记录 |

自然语言完成声明使用固定判定规范并进行盲态人工复核；不得只靠关键词识别。客观产物是否合格仍由确定性裁判判断。

建议投资门槛：相对 A 的目标错误完成率下降至少 50%，误阻断率不超过 5%，合格交付率不下降，月净收益为正；另报告 C 相对 B 的增量。安全回归中必须没有证据伪造被接受。门槛是决策目标，不是可靠性保证。

小样本只能作筛选。基线没有出现目标错误时，不能报告“改善 100%”；扩大代表性场景并报告计数与不确定性。比较结果接近或不稳定时不扩大强制模式。真实模型执行必须显式触发，不加入默认付费 CI。

## 7. 决策边界

- **继续**：两类均有可复现收益，成本与误阻断满足门槛，维护责任明确。
- **缩小**：仅一类受益，则仅启用该类；保留通用接口但不扩展额外框架。
- **停止扩展**：净收益非正、基线已足够好、规则长期不稳定或无法控制交付边界。

最终收益不是“让模型变得确定”，而是让指定工作中的完成条件可检查、证据可追踪、失败可解释。强制条件以外的质量仍需业务判断。

## 8. 可选阶段 5：独立审查的增量 ROI

启动条件：阶段 4 已形成门禁实测报告，仍存在机械检查难以覆盖的需求遗漏或逻辑缺陷，且维护者决定为指定任务增加审查。未启动不影响首期完成。角色提示词可以复用现有 Skills，阶段 5 的投入重点是职责隔离和交付约束。

估算新增 **5–9 人日**，用于受限审查子代理、版本化审查记录、收尾接入、故障回归和评估整理；付费推理及等待另计。该估算建立在阶段 1–4 已完成的基础上，不包含全面角色管理或新的通用权限系统。首期仍为 20–33 人日，选择该阶段后累计约 25–42 人日。

增加 D 组：与 C 组相同的门禁和 Skill，加独立审查。针对固定的审查适用场景重新交错运行 C/D，保持模型、预算及环境一致，不将旧 C 结果与新环境的 D 直接比较。初始每类选择 5 个复杂场景，每组每场景 3 次，共 60 次额外试次；包含植入遗漏和无缺陷样本。原有 180 次首期实验不变。

重点统计 C 未发现而 D 发现并修复的真实缺陷、误报处理时间、修正引入的新问题、总费用和人工审查节省。发现条数不是成功指标；缺陷由独立裁判及盲态人工复核确认，不能由审查者自行证明其价值。相同模型的新上下文仍可能产生共同错误。

新增审查净收益 = 少返工及少人工核验的收益 − 额外推理、等待、误报处理与维护成本。

扩大条件：D 相对 C 的目标错误完成率下降至少 50%，误阻断不超过 5%，合格交付率不下降，新增审查净收益为正，且审查权限及证据回归通过。以上为待验证目标；零基线或小样本不稳定时继续观察，不宣称改善。允许只在受益的一类任务启用；不满足条件则保持关闭。
